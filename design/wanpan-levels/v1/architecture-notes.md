# 完攀日记账户等级与徽章 · 技术方案 v1

状态：设计与实施方案，2026-09-06 基于本地代码审计。未接入真实账号、未修改生产业务代码、未执行数据库迁移。等级阈值是产品初版配置，尚无真实用户分布校准。

## 1. 产品定义与等级配置

账户成长显示 `Lv.0–Lv.10`，表达积累和热爱。线路难度继续显示 `V0–V17`，表达线路难度；两者没有换算关系。沿用“累计使用行为、两项门槛、逐级成长”的交互思路，不复制其他产品的视觉或未核实规则。

等级只由两项累计有效事实决定，不新增 XP 或虚拟货币：

- 累计有效攀爬日 D：北京时间一个自然日内至少保存一次有效完攀，记 1 天。
- 累计完攀线路 U：同一用户同一线路 ID 在有效记录中只计 1 条。重复线路不同日期可增加 D，不增加 U；同一天多条线路增加 U，D 仍只加 1。
- 升级必须同时满足两项门槛。V 难度、尝试次数、点赞、登录、分享、消费和普通动态均不增加等级进度。
- 私密和岩友可见的有效完攀同样累计。休息、断签、跨月和长期不登录不会减少有效记录，也不会自动降级。
- 本产品目前只有“已完攀 + 尝试次数”，没有“练习了但未完攀”的事实模型。因此第一版不把未完攀练习计为攀爬日。

| 等级 | 名称 | 累计攀爬日 D | 累计不同线路 U |
| --- | --- | ---: | ---: |
| Lv.0 | 新岩友 | 0 | 0 |
| Lv.1 | 初次上墙 | 1 | 1 |
| Lv.2 | 渐入佳境 | 3 | 8 |
| Lv.3 | 岩馆常客 | 7 | 25 |
| Lv.4 | 稳步向上 | 15 | 60 |
| Lv.5 | 攀爬成习 | 30 | 120 |
| Lv.6 | 心有岩点 | 60 | 250 |
| Lv.7 | 百日攀友 | 100 | 500 |
| Lv.8 | 千线旅人 | 180 | 1,000 |
| Lv.9 | 攀行不止 | 300 | 1,800 |
| Lv.10 | 热爱成章 | 500 | 3,000 |

```text
currentLevel = max(L where D >= minDays[L] AND U >= minRoutes[L])
remainingDays = max(0, minDays[nextLevel] - D)
remainingRoutes = max(0, minRoutes[nextLevel] - U)
```

界面分别显示两个进度条和剩余量，不把平均进度伪装成升级判定。Lv.10 显示“当前最高等级”，不再显示不存在的下一级。Lv.0 是无徽章的新岩友起点，显示待解锁状态，不生成基础徽章；Lv.1–10 对应共 10 枚徽章，达到条件自动授予，不需要点按钮才升级。

徽章权益仅用于身份展示、佩戴和收藏，不付费购买、不售卖升级，不以等级锁住记录完攀、查看线路等核心功能。

理论节奏示例：若每周在不同日期攀爬 2 次，每次完成 6 条此前未计数的新线路，则每周增加 2 天、12 条。双条件下，Lv.5 需要 `max(30÷2, 120÷12)=15` 周；Lv.10 需要 `max(500÷2, 3000÷12)=250` 周。此为连续按该节奏记录且无撤销的数学演示，不是真实用户数据或训练目标；门槛需根据上线后的用户分布校准。

## 3. 数据结构与单一计算入口

第一版沿用 PostgreSQL + Fastify，不引入 Redis、消息中间件或额外积分流水。建议新增以下表；字段是实现合同草稿，不是已执行 SQL。

### `climbing_facts`：可审计的完攀事实

字段：`id`、`user_id`、`source_send_id`、`source_route_id`、`route_identity`、`occurred_at`、`local_date`、`source_kind`、`client_request_id`、`request_hash`、`status`、`invalidated_at`、`invalidation_reason`、`created_at`。

- 每次新客户端明确保存完攀时新增事实。`local_date` 从服务端 `occurred_at AT TIME ZONE 'Asia/Shanghai'` 固化，客户端无法通过改时区或日期增加天数；长视频跨午夜按保存确认日记账，第一版不开放任意补签。
- `source_kind` 区分 `checkin`、`submission_video`、`legacy_backfill`，不存文案、媒体等冗余个人内容。
- `(user_id, client_request_id)` 对有幂等键的请求唯一。请求 ID 相同且有效载荷不同返回 `409 IDEMPOTENCY_KEY_REUSED`；重试复用已保存结果与原日期。
- `route_identity` 保存稳定线路 UUID；在现有规模以线路 ID 去重。相同物理线路被用户重复投稿成多个 UUID 无法自动识别，需运营合并/撤销；不声称已实现真实线路自动查重或完攀真实性证明。
- `source_send_id` 与 `source_route_id` 可使用 `ON DELETE SET NULL`，便于业务删除前先完成有效性转移和审计；不能把自然下架、换线、过期直接等同作弊。自然下架保留历史事实；用户删除记录、明确撤销假记录则失效。
- 对有效事实建 `(user_id, local_date)`、`(user_id, route_identity)` 索引。D、U 从有效事实 distinct 聚合，先保证可重建；只有经数据量验证有必要时才做计数增量优化。

### `user_growth`：服务端读取快照

字段：`user_id PK`、`climbing_days`、`unique_routes`、`current_level`、`rules_version`、`revision`、`updated_at`、`backfill_status`。

`user_growth` 是可重算缓存，事实表是依据。统一 `GrowthService.recomputeAndAward(client, userId)` 负责重算、配置判级和授予。`rules_version` 冻结为 `levels.json` 中的 `wanpan-growth-v1`；调整阈值需明确迁移策略，不能静默修改而让已有用户突然变化。

### `user_badges`：权益与收藏记录

字段：`id`、`user_id`、`badge_key`、`level`、`rules_version`、`earned_at`、`status`、`revoked_at`、`revocation_reason`；唯一 `(user_id, badge_key, rules_version)`。`earned_at` 与前端是否打开庆祝无关。

Lv.0 不写入徽章表，只表示待解锁起点；Lv.1–10 对应固定 `badge_key=account-level-01…10`，共 10 枚。一次跨多级应补齐全部徽章，庆祝只突出当前最高一级，附“同时点亮 N 枚徽章”。

### `growth_presentations`：自动庆祝去重

字段：`id`、`user_id`、`from_level`、`to_level`、`badge_ids`、`growth_revision`、`kind`、`status`、`consumed_at`、`invalidated_at`、`created_at`。对 `(user_id, growth_revision, kind)` 唯一；`status` 区分 `pending`、`consumed`、`superseded`、`invalidated`。

“自动获得徽章”和“自动播放动效”分开。徽章权益由唯一约束保证；展示回执只决定哪个设备自动播放。历史补授和离线期间多次升级形成一场以当前最高有效等级为主角的庆祝，其余本次新徽章合并展示，不逐条播放旧事件。

## 4. 事务、重试与跨端

所有成长写路径按一致顺序执行：

1. 验证身份、请求、线路和当前操作意图；为账号创建 `user_growth`（冲突忽略），再 `SELECT … FOR UPDATE` 锁该账号成长行。
2. 检查客户端请求 ID 及哈希；已成功的重试返回相同结果引用，不增加事实、不移动日期、不再次授予。
3. 执行原有 `sends` upsert 或带视频投稿；保存新的完攀事实。只编辑文案、可见性、视频替换的操作不算新一天；客户端把编辑与“再次记录完攀”作为不同意图，服务端分明确端点或操作枚举。
4. 从有效事实重算 D/U/等级；更新 revision；用 `INSERT … ON CONFLICT DO NOTHING` 授予新徽章。仍在账号成长行锁内合并未展示的新徽章，将已有待展示事件标为 `superseded`，生成一条引用当前 revision、以当前最高有效等级为主角的汇总事件。恢复曾获徽章只更新原记录状态，不生成该徽章的自动庆祝。
5. 事务提交后返回成长快照与展示事件 ID。数据库失败整体回滚；前端永远先确认保存成功再庆祝。

统一锁顺序为“成长行 → 业务行 → 事实 → 奖励”，删除、审核、补历史也遵循此顺序。这样同用户跨端并发在同日只增加一天、同线路只增加一条，跨级只授予一次，不依赖客户端节流。

新客户端在进入提交草稿时创建 UUID，网络重试及进程恢复复用它；切换账号使草稿失效，不把上一账号的请求/动画交给下一账号。请求成功后，下一次明确完攀才创建新 ID。

旧客户端没有请求 ID，服务端无法严格区别“昨日响应丢失后重试”和“今日再次完攀”。兼容策略应明确：旧客户端仍可正常发布和更新原有动态；新线路首次保存按 `legacy:send:<send_id>` 计一次成长，重复线路的新增攀爬日需升级客户端后使用明确的完攀事件。不要以 `now()`、随机 UUID 或当天哈希假装解决跨午夜重试。

推荐 API：

| 接口 | 契约 |
| --- | --- |
| `GET /api/growth/config` | 返回版本、Lv 阈值、徽章 key、资产版本，可缓存 |
| `GET /api/users/me/growth-level` | 返回 D/U/currentLevel/nextLevel/两个剩余量/revision/回填状态；需登录 |
| `GET /api/users/me/badges` | 返回拥有、未达成、撤回状态；需登录 |
| `POST /api/users/me/growth-presentations/consume` | 账号事务锁内验证有效徽章、跳过失效/过期事件、合并未展示升级，再原子消费当前最高有效等级的一场庆祝；只有一端拿到 `shouldPresent=true` |
| 原 `POST /api/sends` 和 `POST /api/submissions` | 添加请求幂等键和可选成长返回字段；保留原合同供旧客户端解析 |

动效消费沿用“成长行 → 徽章 → 展示事件”的锁顺序，在同一事务内重新验证当前有效徽章和成长 revision：撤回徽章关联事件标为 `invalidated`，过期 revision 的事件标为 `superseded`，仍有效且未展示的新徽章归并到当前最高有效等级的一场庆祝。合并、替代旧事件、写入 `consumed_at` 与状态回执必须原子完成；没有有效待展示新徽章时返回 `shouldPresent=false`。这样手机和小程序并发消费时只有一端自动弹出，离线积压也不会按最早事件逐场播放。

消费成功但客户端随即崩溃时，自动动画可能没有完整播放；徽章仍已获得，可在详情手动重播。不能保证跨设备在崩溃场景中“视觉播放严格一次”，可以保证授予一次和消费一次。手动重播不请求新奖励、不触发成就数据写入。

## 5. 删除、无效记录与历史补发

默认保持现有“删除打卡后统计更新”的语义：删除动态时，先将这个 `send` 关联的事实失效，再删除内容并同步重算。删除界面需展示实际影响，例如“将删除这条线路的完攀记录，成长进度也会更新”；若未来需要“只隐藏动态、保留攀爬记录”，应提供独立操作，不能暗中更改现有删除语义。

有效数据减少导致不再满足门槛时，当前等级重算，相应等级徽章变为 `revoked`；详情可标注“记录已撤销”，不能继续当成当前有效徽章佩戴。删除或违规撤销导致等级变化时，在同一成长事务锁内使相关待展示事件失效，若仍有其它有效且首次获得后尚未展示的徽章，再按当前最高有效等级合并一场；不得让已撤回徽章继续被 consume 返回。

再次满足同一徽章条件时恢复原唯一记录，保留首次 earned_at，使用状态变更审计；不制造第二枚同 key 徽章，也不再次自动庆祝同一枚徽章，详情仍可手动重播。普通休息不减少事实；自然换线、线路归档不扣成长；本人删除完攀记录、确认虚假或误记时，执行对应事实撤销和重算。

如产品希望正常删除后保留永久荣誉，须另立“历史荣誉”概念，并把当前有效等级和历史最高等级分别命名。本 v1 不混用这两种解释。

历史导入原则：

1. 不按账号年龄、注册日、点赞数或缺失日期猜攀爬天数。现有唯一 `send` 只保存首次创建和最近提交，无法恢复中间重复日期。
2. 建议只用现存 approved、关联有效线路的 `sends.sent_at` 为每条记录补一个事实，保留与当前日历一致的可证明日期；`source_kind=legacy_backfill`。`created_at` 可作为审计参考，但不自动算第二个攀爬日，因为旧记录可能先 pending 后转 approved。
3. 每条源记录使用确定性键，批处理可重跑；按用户锁读取当前状态，不覆盖上线后新事件。用户删掉后不能被回填再次复活。
4. 先部署事实写入，再以迁移标记/游标补历史；对同一源 `send` 做去重，校验历史与实时重叠，最后按用户重算。记录 source 时间和迁移时间，不能把补发当天误算成全员攀爬日。
5. 历史已被删除的真实完攀与被 upsert 覆盖的日期无法恢复，界面说明“历史等级根据仍保留的完攀记录计算”，不承诺补齐实际全部攀爬日。
6. 回填跨多级时自动授予所有相应徽章，首次打开只展示最高级及本次补发汇总；`earned_at` 记录实际授予时间，若推导历史达标时间则另用字段，不伪造精确日期。

## 6. 客户端与动效合同

Flutter 新增 `GrowthRepository`、`GrowthSnapshot`、`UserBadge`、`GrowthPresentation`，沿 `ClimbingActivityChanges` 刷新。每个账号的成长快照按服务端 revision 单调更新；陈旧响应的 `growth_revision` 不得覆盖更高 revision 的快照，也不得用陈旧展示事件触发庆祝。账号切换时清除该会话的待展示内容；小程序遵循同样规则。账户徽章与 V 级最高难度分别命名；若同时发生，成功页面合并显示两条结果，只安排一个主庆祝，默认账户升级优先、最高 V 作为结果补充。

徽章资源使用稳定 asset key。动态 Lv 标签、名称、进度和“已获得”文字由 Flutter/小程序原生文本绘制，支持语义朗读和配置调整。概念徽章图上的固定数字属于该枚徽章的视觉识别，不能作为程序判级来源；生产稿需与资产 key 一起校验。静态徽章资源与动效中的中心徽章必须来自同一视觉版本，不能庆祝后变成另一枚徽章。

获得流程：保存结果确认 → 单次徽章弹出、落定 → 等级及名称出现 → “收下徽章/查看徽章”操作。按钮为关闭与导航，不是补写权益。动画总长 1.1 秒（60 fps，共 66 帧），0.9 秒时徽章稳住，随后保持最终画面；结果卡持续展示，直到用户主动关闭或导航离开。可随时跳过，不阻塞返回；默认静音，音效按现有偏好控制；触觉一次且失败不影响结果。减少动态时直接显示落定徽章与文字、最多短淡入，取消旋转/粒子/大幅位移。

小程序按同一 API 显示等级、收藏状态与两个进度；若其动效运行时不支持某种资产，使用相同静态徽章加原生渐显。跨端权益与幂等一致不依赖视觉播放能力。预览里的示例等级与统计必须标注演示，不能冒充账号真实成长数据。

## 7. 实施顺序与验收

阶段 1：冻结 v1 配置、资产 key 与删除语义；增加数据库表和统一成长服务，先做幂等与统计测试。阶段 2：接入两个完攀写入口、删除和账号注销；批量回填并抽样核对。阶段 3：接入 Flutter 等级入口、徽章页和庆祝，补小程序静态合同。阶段 4：观察等级分布和异常增长，再决定是否调整后续新规则版本。

必须验证的场景：

- D 达标/U 未达标以及 U 达标/D 未达标都不升级；恰好双达标升级；Lv.10 的 nextLevel 为 null。
- 同天多路线只加一天；同路线跨日加天不加线路；同请求重复及跨午夜响应丢失重试不加数据。
- 2 个客户端并发保存同路线/不同路线只授予一次；同幂等键不同载荷报冲突；旧客户端不重复记账。
- 普通动态、无视频仅投稿、点赞、可见性变更不加成长；私密有效完攀计成长但不泄露明细。
- 删除、违规撤销、恢复、自然换线、用户注销、回填重跑和回填与实时写入交错均符合上面的数据语义。
- 保存成功响应丢失后重试能恢复徽章；跨端只有一端自动消费庆祝；中途退出后徽章仍存在；手动重播不再发奖。
- 删除/撤销后待展示事件失效，consume 不返回无效徽章；离线期间多次升级合并最高有效等级的一场，其余徽章汇总；恢复曾获徽章不再次自动庆祝；陈旧 revision 不覆盖新快照。
- 长中文、紧凑屏幕、弱网/离线、切换账号、减少动态及动效加载失败使用同一状态和静态落图。
